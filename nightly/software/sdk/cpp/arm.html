Arm Control — C++ Example ​

C++ · Python

Source: rbq_sdk/cpp/example/src/arm/

Controls the RBA-1 arm on an RBQ from an external app. The examples are numbered in the order to try them. Each one does one thing and exits, and each one starts the arm itself when it is not running (arm_helper.hpp), so any of them can be run on its own.

ExampleLevelWhat it does
00_arm_help—Prints the SDK version, then lists the examples and how to run them
01_arm_stateStatePrints the state of the arm joints and the end effector twice a second. Sends nothing
02_arm_powerSetupStarts the arm, prints its status, takes its joints back from a joint-level app, or stops the arm (arm emergency stop) and clears the stop
03_arm_gripperLv1Opens or closes the gripper for a while, then stops it
04_arm_move_jLv1 (joint space)MoveJ to a built-in pose, or to joint angles — all six joints or one, to the angles or by them
05_arm_move_lLv1 (task space)MoveL to a position, RotateL to an orientation, or both; or a short sequence of relative moves
06_arm_high_levelLv1 (task space)Drives the end effector with a gamepad on this PC
07_arm_low_levelLv0 (joint level)Takes the six arm joints, streams joint references at 500 Hz and gives them back. For your own FK / IK, change my_arm
08_arm_torqueLv0 (torque)Takes the six arm joints and sends joint torques at 500 Hz: gravity compensation and a spring toward the start pose

WARNING

The arm moves fast enough to hurt. Keep people out of its reach, start with small moves, and keep the remote E-Stop at hand.

Prerequisites ​

  • The SDK installed. On a PC that never had it, follow C++ SDK Overview. Otherwise go straight to Build. If the build stops with The SDK installed in … is not this checkout's SDK, install it again and build again:

    bash
    cd ~/RBQ/rbq_sdk/cpp/rbq_sdk_cpp     # ~/RBQ: where you cloned this repository
sudo bash scripts/build.bash

  • The robot stack running — the simulator on this PC, or a robot this PC reaches.

  • An RBQ with the RBA-1 arm, standing. In the simulator start it with bash scripts/sim.bash --robot rba-1, then Auto Start → STAND in the web UI.

Build ​

bash
cd ~/RBQ/rbq_sdk/cpp/example      # ~/RBQ: where you cloned this repository
bash scripts/setup.bash
bash scripts/build.bash

Binaries: bin-x86_64/00_arm_help … bin-x86_64/08_arm_torque, bin-x86_64/my_arm, and the test tool bin-x86_64/arm_cli (see ArmClient)

Run every example from this folder, rbq_sdk/cpp/example/ — the commands on this page start with ./bin-x86_64/.

Every example takes the target as its first argument: where the example connects — the robot stack it reads from and sends to. Leave it out to use the simulator; give robot (-r) to send commands to the robot:

TargetConnects to
sim (-s), or nothingThe simulator on this PC
robot (-r)The robot at 192.168.0.10, through whichever network device of this PC reaches it — connect to the robot's Wi-Fi or cable first
a network device name of this PC, such as enp3s0The robot stack reached through that device, as in the rbq examples. ip -br link lists the names

A word that is none of these is not a target. The example takes the simulator and reads the word as its next argument, and stops with no target given, so '…' was read as an argument when that argument is wrong.

00_arm_help lists the examples and these targets, and every example prints its full description with -h. Keep 01_arm_state open in its own terminal while you run the others.

When a call works, an example prints one line, such as [arm] MoveJDelta done in 0.91 s. When it does not, it prints the reply code, what it means and what to do next. The codes are listed under ArmClient.

1. Arm state — 01_arm_state ​

Prints the six arm joints and the gripper — name, board state, owner, reference and measured position, velocity and torque, gains — and the end-effector pose, twice a second (2 Hz). It only reads; it sends nothing to the robot.

bash
cd ~/RBQ/rbq_sdk/cpp/example
./bin-x86_64/01_arm_state [target]

[target] is where to connect: sim or nothing for the simulator on this PC, robot for the robot — see the target table.

Subscribes to rt/rbq/arm_joint (ArmJointInfo_) and rt/rbq/arm_ee (TaskInfo_) and prints until Ctrl+C:

ColumnMeaning
nameJ0–J5 (J0 shoulder yaw, J1 shoulder pitch, J2 elbow pitch, J3 elbow roll, J4 wrist pitch, J5 wrist roll), GRP (gripper)
stat / errBoard state (NON CON HOM RUN) / error (OK JAM FLT TMP CUR BIG INP)
ownerApp slot that drives the joint
ref_pos / posPosition reference the joint follows / measured position [deg]
ref_vel / velVelocity reference / measured velocity [deg/s]
ref_torque / torqueFeed-forward torque reference / measured torque [Nm]
kp / kdGains the joint actually applies [Nm/rad], [Nm·s/rad]
cur / T(b/c)Current [A] / board and coil temperature
EE lineEnd-effector position [m] and roll/pitch/yaw [deg] in the body frame

kp is 0 until the arm is started.

2. Start the arm — 02_arm_power ​

Starts the arm (axis initialization and reference streaming), prints its status, takes back the joints a joint-level app holds, or stops the arm and clears the stop.

bash
./bin-x86_64/02_arm_power [target] [on|status|release|estop|clear]
ActionDoes
on (default)Starts the arm if it is not running (AutoStart) and waits until it is
statusPrints the arm status (GetState): arm_type, con_start, task_control, estop, pose, joint_owner, sdk_slot and the rest listed under ArmClient
releaseGives every arm joint a joint-level app holds back to the arm controller (ReleaseJoints)
estopArm emergency stop (EmergencyStop)
clearEnds the arm emergency stop (ClearEmergencyStop)

Arm emergency stop. The arm joints keep only damping: they no longer hold a position. The arm sinks slowly under its own weight and gives way when it is pushed or hits something, instead of dropping or pushing back.

  • It stays on until clear (or AutoStart). Until then every motion call is refused with 7108, and the examples stop with the arm is in emergency stop - clear it first. The gripper still works.
  • The robot's E-Stop (the app's E-STOP, SportClient::Damp, rt/rbq/cmd/emergency) stops the arm the same way. Unlike the arm-only emergency stop, it ends by itself when the legs stand up again, and the arm holds the pose it sank to. clear also ends it before that. The arm emergency stop stops only the arm, whatever the robot is doing.
  • After clear the arm holds the pose it sank to. Move it to Ready (04_arm_move_j 1) before task-space moves.

3. Gripper — 03_arm_gripper ​

Opens or closes the gripper for a set time (1 s by default), then stops it.

bash
./bin-x86_64/03_arm_gripper [target] <action> [seconds]

# Close for 1 s (the default), then stop:
./bin-x86_64/03_arm_gripper sim 1

action is 0 or open, 1 or close. The gripper keeps moving until it is stopped. This example stops it after seconds (0 < seconds ≤ 5).

The gripper also moves from a gamepad (6), and an app that holds the arm joints can still open and close it (7).

4. Joint-space move — 04_arm_move_j ​

Moves the arm to one of four built-in poses, or by joint angles. The arm controller moves the joints there, all arriving together.

bash
./bin-x86_64/04_arm_move_j [target] <pose>
./bin-x86_64/04_arm_move_j [target] [abs|rel] <J0 J1 J2 J3 J4 J5> [seconds | vel=<deg/s> acc=<deg/s^2>]
./bin-x86_64/04_arm_move_j [target] [abs|rel] J<n> <degrees>      [seconds | vel=<deg/s> acc=<deg/s^2>]

./bin-x86_64/04_arm_move_j sim 1                      # Ready
./bin-x86_64/04_arm_move_j sim home                   # Folding
./bin-x86_64/04_arm_move_j sim 0 120 -60 0 -60 30 4   # all six joints to these angles in 4 s
./bin-x86_64/04_arm_move_j sim J1 120 2               # only J1, to 120 deg in 2 s
./bin-x86_64/04_arm_move_j sim rel J4 -15 vel=20      # only J4, -15 deg from where it is, at most 20 deg/s

Run it without arguments to see the poses and these forms.

Give the pose as a number or a name, in any case — 0 and home are the same.

NumberNameAngles J0–J5 [deg]Pose
0home0 0 0 0 0 0Home / walking pose
1ready0 140 -70 0 -70 0Start pose for task-space moves. The first move after the arm starts goes here
2straight0 90 -180 0 0 0The arm stretched straight up
3pickup0 150 -100 0 40 0To pick up an object from the ground

MoveJ() itself takes the pose name: ARM_POSE_FOLDING, ARM_POSE_READY, ARM_POSE_STRAIGHT, ARM_POSE_PICKUP_READY. The numbers and names belong to the example.

The example goes straight to the pose you chose, from wherever the arm is.

By joint angles [deg]:

ArgumentMeaning
abs (default)The angles are where the joints go (MoveJ)
relThe angles are how far the joints turn from where they are commanded now (MoveJDelta)
J0 … J5Six angles, one per joint
J<n> <degrees>Only joint n (J0–J5). The other joints stay
secondsEvery moving joint arrives in this time, 0.5 to 20 s
vel= acc=Or the robot picks the shortest time that keeps the fastest joint under these — see speed

The joints reach J1 0°–180°, J2 −180°–2°, the others −360°–360°. Ready is 0 140 -70 0 -70 0. A move that ends at the Ready angles counts as Ready, so ControlStart() works after it.

  • Before a joint move starts, the robot follows its path. If the arm would come within 2 cm of the body or the legs, the move does not start and Wait() returns 7106. Move the end effector away from the robot (section 6), then try again.
  • During the move, a joint that pushes much harder than holding the arm needs (a collision) stops the move, and Wait() returns 7105. GetState collision_joint names the joint.

5. Task-space move — 05_arm_move_l ​

Moves the end effector to a position, an orientation or both, or runs a short sequence of relative moves.

bash
./bin-x86_64/05_arm_move_l [target]                                                 # demo
./bin-x86_64/05_arm_move_l [target] [abs|rel] pos  <x y z>                [seconds | vel= acc=]
./bin-x86_64/05_arm_move_l [target] [abs|rel] ori  <roll pitch yaw>       [seconds | ang_vel= ang_acc=]
./bin-x86_64/05_arm_move_l [target] [abs|rel] pose <x y z roll pitch yaw> [seconds | vel= acc= ang_vel= ang_acc=]

# Demo: up 2 cm, forward 2 cm, pitch +10 deg, then back the same way:
./bin-x86_64/05_arm_move_l sim

# To a position [m] in 3 s - the orientation stays:
./bin-x86_64/05_arm_move_l sim pos 0.80 0 0.20 3

# To pitch 30 deg in 2 s - the position stays:
./bin-x86_64/05_arm_move_l sim ori 0 30 0 2

# 5 cm back from where it is, in 2 s:
./bin-x86_64/05_arm_move_l sim rel pos -0.05 0 0 2
ModeCallMoves
posMoveL(x, y, z, …)The position. The orientation stays
oriRotateL(roll, pitch, yaw, …)The orientation. The position stays
poseMoveL(x, y, z, roll, pitch, yaw, …)Both

abs (the default) gives where the end effector goes. rel gives how far it moves: MoveLDelta and RotateLDelta. The position is added to where the end effector is commanded now, so repeated moves do not drift. The angles are added to the roll / pitch / yaw it measures now; repeated turns can drift by a few tenths of a degree each.

Without the word, three numbers are pos and six are pose. Positions [m] and roll / pitch / yaw [deg] are in the body frame — the numbers the EE line of 01_arm_state shows: x forward, y left, z up; the orientation turns about z (yaw), then y (pitch), then x (roll). Give seconds (0.5 to 10 s), or the limits of speed.

If task-space control is off, it goes to Ready and turns it on (ControlStart) first. If it is already on (task_control is 1 in GetState), the arm moves from where it is.

The end effector stays in the workspace of section 6. A move that reaches its edge stops there, and Wait() returns 7107.

6. Gamepad task-space control — 06_arm_high_level ​

Drives the end effector with a gamepad on this PC. The sticks set its velocity, sent 50 times a second.

bash
./bin-x86_64/06_arm_high_level [target] [fast] [joystick]

# With the first gamepad found on this PC:
./bin-x86_64/06_arm_high_level sim

# Full stick at the robot's limit, 0.5 m/s and 0.8 rad/s:
./bin-x86_64/06_arm_high_level sim fast

You drive the end effector with a gamepad plugged into this PC (Logitech F710 in X mode, or any pad the rbq examples take). The example turns task-space control on, going through Ready first if it is off. It then switches the arm to external control and sends end-effector velocities 50 times a second.

The buttons are the same as in the app's manual control (Start manual control). Holding RB changes what the sticks do.

Directions are those of manual control: x forward, y left, z up.

TopicTypeFields

rt/rbq/cmd/arm/high_levelArmHighLevelCommand_lin_vel[3] [m/s], ang_vel[3] [rad/s], gripper (1 open, -1 close, 0 stop)
  1. External control works only while task-space control is on (task_control is 1).
  2. Keep publishing, including all-zero commands. If no command arrives for 0.5 s, the arm stops.
  3. The robot limits the speed to 0.5 m/s and 0.8 rad/s and keeps the safety checks of the app joystick.
  4. The robot's own gamepad takes priority. If its sticks are moved for 0.3 s, external control turns off and high_level in GetState becomes 0. The example then quits. An arm emergency stop (02_arm_power estop) turns it off too. A browser with the robot's web page or the app open reads a gamepad plugged into the same PC, so moving the sticks drives the robot as well. Close that page, or use another gamepad there.
  5. Only the arm moves. Unlike manual control, the body does not lean or turn to follow the end effector.
  6. The end effector works only in front of the robot. The gripper cannot go over, beside or behind the body, whatever is mounted on it. It stops about 0.55 m in front of the body center, measured at the wrist.
  7. At full reach the arm stops. Pushing further outward does nothing. Pull back, or move sideways.
  8. The arm stops 3 cm before it touches the body or a leg, with any part of it. Move the other way to continue.
  9. The robot holds the target at most 5 cm and about 9° ahead of the arm. When the arm cannot follow, the target does not run away, so the arm moves as soon as you push the other way.

7. Joint-level control — 07_arm_low_level ​

Takes the six arm joints, sends joint references from your program 500 times a second, and gives the joints back. Out of the box it moves one joint out and back.

This is the expert level. Your program sends every joint reference itself, and the arm controller no longer plans the motion or checks the workspace. Try 04–06 first.

bash
./bin-x86_64/07_arm_low_level [target] [joint] [delta_deg] [seconds] [grip]

# J0 (shoulder yaw) 20 deg out and back in 4 s:
./bin-x86_64/07_arm_low_level sim 0 20 4

# The same, closing the gripper on the way out and opening it on the way back:
./bin-x86_64/07_arm_low_level sim 0 20 4 grip
ArgMeaningDefault
targetsim / robot (see Build)—
joint0–5 = J0–J50
delta_deghow far to move it [deg], |delta_deg| ≤ 3015
secondsout and back again, 2–20 s4
gripalso close the gripper on the way out and open it on the way back. The gripper is left opening: stop it with 03_arm_gripper or GripperStop()off

Out-of-range values print the usage and exit without sending anything.

How it works ​

  1. Starts the arm and goes to Ready.
  2. Creates, for app slot 22, a Publisher<MotionRef_> on rt/rbq/ref/motion/_22 and a Publisher<JointOwnershipCmd_> on rt/rbq/cmd/motion/owner/_22, and subscribes to rt/rbq/arm_joint.
  3. Reads ref_position, kp and kd of the six arm joints from rt/rbq/arm_joint.
  4. Publishes a first reference equal to what the arm already follows, then sends JointOwnershipCmd_ with arm_joint[0..5] = true. The legs and the gripper stay with the robot.
  5. Publishes arm_joint[] at 500 Hz with the arm's own gains, moving the chosen joint on a smooth (cosine) path out and back.
  6. Holds the last reference for 0.2 s, then sends arm_joint[0..5] = false and exits. Ctrl+C stops the move where it is and gives the joints back there.

Steps 1–4 and 6 are in arm_helper::JointStream (arm_helper.hpp); step 5 is Controller in 07_arm_low_level.cpp.

Your own algorithm ​

src/arm/my_arm.cpp is the file for your own FK / IK or planner. It is already in src/arm/CMakeLists.txt and builds with the examples, so change it as you like. It has two parts: Controller, which you change, and main, which starts the arm, takes the joints, calls Controller 500 times a second, sends what it returns, and hands the joints back. It first moves the arm to Ready, so the start pose is Ready. As shipped, Controller moves every joint ±10° around the start pose on a sine (period 4 s) twice and ends where it started, after 8 s. Run with a gamepad, it jogs the joints with the sticks instead (see Gamepad). Run with torque, it moves the same sine by torque (see Joint command and torque reference).

MemberWhenWhat it does
Start(s, arm)Once, after the joints are takens.qRef is where the arm is now
Update(t, s, pad, cmd, arm)Every tick (500 Hz)t is the time since Start [s], pad the gamepad now (Gamepad). Change cmd, the joint command: set cmd.q to the six joint references [rad] for position control (Joint command). Return false to end

  1. Put your algorithm in Controller, between >>> YOUR ALGORITHM and <<< YOUR ALGORITHM. This one moves the end effector 5 cm up and back down in 8 s with your own FK and IK (MyFK, MyIK):

    cpp
    // Your own kinematics - in this file or in your own library.
void MyFK(const float q[kArmJoints], float p[3]);                                 // joint angles -> end-effector position
bool MyIK(const float p[3], const float seed[kArmJoints], float q[kArmJoints]);  // false when p is out of reach

struct Controller {
    float p0[3];             // end-effector position at the start
    float qLast[kArmJoints]; // last joint references - the seed of the next IK

    void Start(const ArmState &s, JointStream &arm)
    {
        (void)arm;
        std::copy(s.qRef, s.qRef + kArmJoints, qLast);
        MyFK(s.qRef, p0);
    }

    bool Update(double t, const ArmState &s, const Pad &pad, Command &cmd, JointStream &arm)
    {
        (void)s;
        (void)pad;
        (void)arm;
        const double T = 8.0;
        if (t > T) return false;

        // >>> YOUR ALGORITHM: the end effector 5 cm up and back down in T seconds
        const float lift = 0.05f * 0.5f * static_cast<float>(1.0 - std::cos(2.0 * M_PI * t / T));
        const float target[3] = {p0[0], p0[1], p0[2] + lift};
        if (MyIK(target, qLast, cmd.q))   // writes the joint references into cmd.q
            std::copy(cmd.q, cmd.q + kArmJoints, qLast);
        else
            std::copy(qLast, qLast + kArmJoints, cmd.q);   // out of reach: stay where it is
        // <<< YOUR ALGORITHM
        return true;
    }
};

  2. Build it and run it in the simulator first:

    bash
    cd ~/RBQ/rbq_sdk/cpp/example
bash scripts/build.bash
./bin-x86_64/my_arm sim

    It ends when Update returns false, or on Ctrl+C. Either way the arm stays where the last reference put it.

To add another program of your own, put its .cpp file in src/arm/ and add its name (without .cpp) to ARM_EXAMPLES in src/arm/CMakeLists.txt. Only the files listed there are built.

What Update gets in s, for J0–J5 unless noted:

FieldUnitMeaning
q, dq, torquerad, rad/s, NmMeasured position, velocity and torque
qRefradReference the arm follows now
kp, kdNm/rad, Nm·s/radGains the arm applies now
owner—App slot that holds the joint (22 while this program runs)
gripperradGripper angle
eePos, eeRpym, radMeasured end-effector position and roll / pitch / yaw, body frame. eeValid is false until the first one arrives

Keep these in mind:

  • Start from s.qRef. A first reference far from it makes the arm travel there at 2 rad/s.
  • Change references smoothly. A reference that moves faster than 2 rad/s is followed at 2 rad/s, and the program prints J… reference jumped ….
  • When your IK has no answer, send the last reference again, as in the example. Never send NaN.
  • Return well within 2 ms. If your algorithm is slower, lower kRateHz. If no reference arrives for 200 ms, the arm holds its position.
  • Check your FK first. Compare MyFK(s.q) with s.eePos at a few poses before you move the arm. Your FK may use another base frame or tool point.
  • arm.Gripper(JointStream::Grip::Open) / Close / Stop opens or closes the gripper. It returns at once, so the loop keeps its rate. arm.Send(q, vel, torque) adds feed-forward velocity and torque. To change the gains, see Gains.

rbq_low_level uses slot 20 and rbq_wheel slot 21, so legs, wheels and arm can run as three apps.

Joint command and torque reference ​

Every tick Update gets cmd, the joint command main sends: for each joint a position q, a velocity dq, a torque tau and the gains kp, kd. Each joint board turns it into a motor torque:

text
motor torque = kp × (q − q_measured) + kd × (dq − dq_measured) + tau

Before each call main fills cmd in, so you change only what you need:

ValueFilled in withEvery tick
qThe position sent last tick (the pose at the start, the first time)No, it stays
dq, tau0Yes
kpThe arm's own: 2632 Nm/rad on J0, J1, 1190 on J2–J5Yes
kdThe arm's own: 21 Nm·s/rad on J0, J1, 9.5 on J2–J5Yes

The three ways to use it below all follow the same sine; put one of them inside this loop, between >>> YOUR ALGORITHM and <<< YOUR ALGORITHM:

cpp
const float T = 4.0f, w = 2.0f * float(M_PI) / T, amp = 10.0f * 0.0174533f;
if (t > 2 * T) return false;
for (int i = 0; i < kArmJoints; i++) {
    const float qDes  = q0[i] + amp * std::sin(w * float(t));   // target position [rad]
    const float dqDes = amp * w * std::cos(w * float(t));       // target velocity [rad/s]
    // one of 1, 2, 3 below
}

1. Position control, no gravity compensation. The joint board follows your position with its PD:

cpp
cmd.q[i]  = qDes;
cmd.dq[i] = dqDes;    // optional: the damping then works around the target velocity and the arm lags less
cmd.kp[i] = 1000.f;   // your gains - leave these two lines out for the arm's own
cmd.kd[i] = 10.f;
// cmd.tau stays 0

Gravity is held only by the error kp builds up, so the lower kp, the more the arm sags.

2. Position control with gravity compensation. The same, plus the gravity torque as a feed-forward:

cpp
cmd.q[i]   = qDes;
cmd.dq[i]  = dqDes;
cmd.kp[i]  = 300.f;          // tau holds the arm against gravity, so a lower kp does not sag
cmd.kd[i]  = 10.f;
cmd.tau[i] = s.gravity[i];   // gravity torque as a feed-forward

The only new line is tau. As the feed-forward carries gravity, kp only pulls the joint back to the target, and you can lower the gains to make the arm soft without it sagging (impedance control).

3. Torque control. The joint board's position control is off, and the torque you send is all the joint gets:

cpp
cmd.kp[i]  = 0.f;            // the joint board's position control off
cmd.kd[i]  = 0.f;
cmd.q[i]   = s.q[i];         // not used with kp 0 - keeps the hand-back smooth
cmd.dq[i]  = 0.f;
cmd.tau[i] = s.gravity[i] + 300.f * (qDes - s.q[i]) + 10.f * (dqDes - s.dq[i]);   // the whole torque is yours

Put any torque in tau - for example s.gravity[i] + 5 for a fixed 5 Nm. my_arm sim torque runs the shipped sine this way, with 300 Nm/rad and 10 Nm·s/rad on J0, J1 and 150 and 5 on J2–J5.

q, dqkp, kdtau
1. PositionYour targetYour gains, or the arm's0
2. Position + gravity compensationYour targetYour gainss.gravity
3. Torques.q, 00Your torque, including s.gravity
  • cmd is per joint, so you can mix: in the loop, torque control on J0 only and position control on the rest. A joint you leave alone keeps the pose it is in with the arm's gains.
  • In torque control, leave s.gravity out and the arm falls, and with no damping term a joint keeps speeding up.
  • Torque control in your program runs at 500 Hz across the network, so high gains get unstable sooner than on the joint board. For a plain soft arm, 2 is the better choice. In the simulator the shipped torque sine lags up to about 5° at the top of the swing and about 1° elsewhere.
  • When Update returns false, main puts the arm's gains back and hands the joints back where the arm is.
  • To put a fixed torque on one joint without writing code, see 08_arm_torque J<n> <Nm>.

Gamepad ​

my_arm reads a gamepad plugged into this PC when you name one, and passes what it reads to Update every tick as pad. What the sticks and buttons do is up to your Controller.

bash
./bin-x86_64/my_arm sim joy                 # the first gamepad found (or $JOY)
./bin-x86_64/my_arm sim /dev/input/js1      # this one

Without a gamepad, pad.connected is false and everything else is 0. As shipped, Controller then moves the joints on a sine. With a gamepad it jogs them:

For example, to move the end effector only while LB is held, and twice as fast with RT pressed:

cpp
bool Update(double t, const ArmState &s, const Pad &pad, Command &cmd, JointStream &arm)
{
    // >>> YOUR ALGORITHM
    if (pad.pressed[PAD_BACK]) return false;
    const float speed = 0.05f * (pad.axis[5] > 0.f ? 2.f : 1.f);   // [m/s]
    if (pad.held[PAD_LB]) {
        p[0] += speed * pad.ly / kRateHz;   // forward / back
        p[1] -= speed * pad.lx / kRateHz;   // left / right
        p[2] += speed * pad.ry / kRateHz;   // up / down
    }
    if (MyIK(p, qLast, cmd.q)) std::copy(cmd.q, cmd.q + kArmJoints, qLast);
    else                       std::copy(qLast, qLast + kArmJoints, cmd.q);
    // <<< YOUR ALGORITHM
    return true;
}
  • The numbers are those of a Logitech F710 in X mode: the switch on the back at X, the MODE light off. Another gamepad may number its buttons and axes differently. Print pad.axis and pad.held to see yours.
  • Joint-level control has no workspace or collision checks. Jog slowly and keep the arm clear of the body.
  • A browser with the robot's web page or the app open on this PC reads the same gamepad and drives the robot with it. Close them, or use another gamepad there.

Gains ​

While your program holds the joints, each joint acts as a spring and a damper around your reference: torque = kp × (reference − angle) + kd × (velocity reference − velocity) + feed-forward torque. JointStream starts with the gains the arm already uses. arm.SetGains(kp, kd) replaces them for every Send() after it.

Start from the gains the arm uses (s.kp, s.kd) and scale them:

cpp
void Start(const ArmState &s, JointStream &arm)
{
    float kp[kArmJoints], kd[kArmJoints];
    for (int i = 0; i < kArmJoints; i++) {
        kp[i] = 0.5f * s.kp[i];   // half as stiff
        kd[i] = s.kd[i];
    }
    arm.SetGains(kp, kd);
    std::copy(s.qRef, s.qRef + kArmJoints, q0);
}
J0, J1J2–J5
Default kp [Nm/rad]26321190

Largest kp / kd the robot applies52 600 / 42023 800 / 189
  • A lower kp makes the joint softer: it gives way when pushed and sags further under the load. Send s.gravity as the feed-forward torque (arm.Send(qRef, nullptr, s.gravity)) to take the sag out.
  • Values above the largest are clamped, not refused. Negative values become 0.
  • These gains apply only while your program holds the joints. The arm controller uses its own gains — set those with SetGains.

N is your app slot, 20–39.

  1. Reference first, then ownership. Start from ref_position, kp and kd in rt/rbq/arm_joint. The arm does not jump at the hand-over.
  2. While an app holds the arm, the arm controller stops and ArmClient motion calls return 3205. The gripper calls still work.
  3. Give back with ownership false. The arm controller holds your last reference, brings its gains back to its own over 2 s and takes your feed-forward torque down to 0 over the same 2 s. If your app stopped while holding the arm, run 02_arm_power [target] release.
  4. Keep publishing — 500 Hz is recommended. If no reference arrives for 200 ms, the arm holds its last position with the gravity torque and damping. In torque mode (kp 0) it floats where it is.
  5. Gains are physical values. The robot converts them for its boards and clamps every value to the joint limits instead of rejecting it. NaN or Inf makes that joint hold.
  6. Each joint reference moves at most 2 rad/s. If a reference jumps further, the arm moves there at 2 rad/s. JointStream prints a warning when it sends such a jump.
  7. Ownership is refused during E-Stop.

8. Torque control — 08_arm_torque ​

Takes the six arm joints and sends joint torques instead of references, 500 times a second: the gravity torque the robot computes plus a spring that pulls every joint back to where it started. With stiffness 0 only gravity is compensated — the arm floats and stays where it is pushed.

It starts where the arm is, so move the arm to the pose you want first (for example with 04_arm_move_j). Only from the folded pose (home, or right after the arm is started) it moves the arm to Ready first.

bash
./bin-x86_64/08_arm_torque [target] [stiffness] [seconds]
./bin-x86_64/08_arm_torque [target] J<n> <Nm> [seconds]

# A 20 Nm/rad spring toward the start pose, for 10 s:
./bin-x86_64/08_arm_torque sim

# Gravity only, for 30 s - push the arm and it stays where it is left:
./bin-x86_64/08_arm_torque sim 0 30

Twice a second it prints the joint furthest from the start pose, its torque and gravity torque, and the end-effector position.

With J<n> <Nm> it puts a torque of your own on one joint: that joint gets the gravity torque plus <Nm> and nothing else, so it turns under that torque, while the other joints get the gravity torque and a 20 Nm/rad spring and stay where they are. Torque mode ​

arm.SendTorque(torque) sends the six torques [Nm] with kp 0 and a small damping kd: 5 Nm·s/rad on J0, J1 and 2.5 on J2–J5 (kTorqueModeKd). Pass your own kd as the second argument. Nothing else holds the arm:

cpp
const ArmState s = arm.State();
float torque[kArmJoints];
for (int i = 0; i < kArmJoints; i++)
    torque[i] = s.gravity[i] + myTorque[i];   // leave s.gravity out and the arm falls
arm.SendTorque(torque);
  • s.gravity comes from rt/rbq/arm_gravity: the torque that holds the arm at the measured angles. The robot computes it from its arm model and takes the body as level, so on a tilted body the arm drifts a little.
  • Each torque is clamped to ±60 Nm on J0, J1 and ±25 Nm on J2–J5.
  • If no torque arrives for 0.2 s, the robot sends the gravity torque with damping itself. The arm floats where it is instead of falling.
  • arm.Send(q) goes back to position control. At the end, arm.Stop() holds the arm where it is with the position gains and gives the joints back.
  • As in section 7, the arm controller's workspace and collision checks do not run.

ArmClient ​

ArmClient works like SportClient: a request/response service (rt/api/arm/request, rt/api/arm/response), and every call blocks until the robot answers. Examples 02–05 use it.

Angles are in radians and angular speeds in rad/s, as in SportClient and the arm topics. The examples take degrees on the command line and convert them before the call.

To try a call without writing code, run the test tool ./bin-x86_64/arm_cli [target]. It is not one of the examples: type a command name such as get_state, auto_start, go_ready, ee_up, gripper_open or estop at the > prompt and it makes that call.

Speed ​

Give each move a time, or speed limits. With limits, the robot picks the shortest time that keeps the move under all of them. 0 or a missing limit takes the default.

A limit above its maximum is refused with 3204. A time you give must keep the move under the maximums too: a shorter one is refused with 7109, and motion_time in GetState holds the time the move needs. The examples print it: 0.5 s is too fast for this move … This move needs at least 0.53 s.

A time the robot picks from the limits is at most 60 s. Wait() gives up after 15 s by default, so for a long move pass it more.

Limits of this preview ​

  • Joint position and torque limits, the speed limits and the gain ranges are provisional until the actuator specifications are final.
  • The gravity torque takes the body as level.
  • The collision checks use the body and leg shapes of the simulator model. Equipment on the top deck is not modeled — that is why the gripper is kept in front of the robot.
  • The collision torque limits are provisional and not yet measured on the robot.
  • Mission-level commands (grasping an object, opening a door) are planned as a separate client.
